This page provides essential guidance for developers creating or adapting plugins for Folia's regionised multithreading architecture. Due to Folia's fundamental architectural changes from traditional Minecraft servers, plugin development requires a different approach to ensure proper functioning in a multithreaded environment.

Understanding the Folia Architecture for Plugin Developers 
Folia's architecture divides the Minecraft world into independent regions, each running on its own thread. This represents a significant departure from traditional Minecraft servers, where all game logic runs on a single "main thread." There is no main thread anymore; each region effectively has its own "main thread" that executes the entire tick loop README.md 18-22

Thread Safety Fundamentals 
Regions tick in parallel , not concurrently. They do not share data, and sharing data without proper context will cause corruption README.md 115-117 
Thread Ownership Model 
Rules for Developers: 
Code running in one region cannot access data in another region README.md 118-120

The Scheduler API System 
Folia replaces the single-threaded BukkitScheduler with specialized schedulers that target specific execution contexts folia-api/paper-patches/features/0002-Region-scheduler-API.patch 4-7 
Scheduler Selection 
Scheduler Use Case RegionScheduler Tasks for a specific world location (chunk/location) EntityScheduler Tasks for a specific entity GlobalRegionScheduler Tasks that affect the whole server or no specific region AsyncScheduler Tasks that do not access game state (I/O, networking) 
Note: The legacy BukkitScheduler is deprecated and its sync methods are largely non-functional in Folia's environment folia-api/paper-patches/features/0002-Region-scheduler-API.patch 34-42

Migration Path 
Migrating from Paper to Folia requires replacing all BukkitScheduler logic and auditing every block of code that accesses entities or chunks.
